The Problem

Moving infrastructure between clouds is hard and risky

Teams that need to migrate from Azure to AWS must rewrite their infrastructure code by hand. This is slow, error-prone, and easy to get wrong.

  • Manual rewrites of Bicep into CloudFormation take time and introduce mistakes.
  • No audit trail — it is unclear why each resource was mapped a certain way.
  • Security risks — secrets can leak and over-permissive rules slip through.
  • Existing tools fall short — they reverse-engineer live accounts or move within one cloud, not source-to-source across clouds.

Why not just ask an LLM?

Asking a model to write CloudFormation directly in one shot is unreliable and unauditable. It can hallucinate syntax, leak secrets, and leaves no record of its decisions.

This project takes a safer, structured approach.

The Solution

A multi-agent pipeline with one reasoning step and human checkpoints

Seven agents work together in a LangGraph state machine. Deterministic code does the parsing, rendering, and deploying. A single LLM call does only the reasoning. Humans approve the important decisions.

AUDITABLE

Structured, not freeform

The LLM emits a structured JSON migration plan — never raw template text — so every decision is reviewable and replayable.

SAFE

Humans stay in control

Plan review and guardrail scanning are automatic checkpoints; only a real stack conflict ever pauses the run for a human decision.

RELIABLE

Self-correcting

Validation failures loop back to the reasoning step with feedback, so the pipeline fixes its own mistakes.

Core Design Principle

Separate reasoning from execution

The key rule: the LLM only reasons and produces a plan — it never writes CloudFormation syntax directly. Everything else is deterministic code.

LLM reasoning (AWS Bedrock)

  • Maps each Azure resource to its AWS equivalent
  • Produces a structured migration plan (resources, parameters, outputs, conditions)
  • One call per run — the only non-deterministic step

Deterministic code (no LLM)

  • Compile Bicep → ARM JSON
  • Build a cloud-neutral representation
  • Render CloudFormation YAML, lint, deploy, verify

Result: an auditable, replayable pipeline where no component makes surprise network calls or mutates AWS state outside the deploy step.

Safety

One human gate, two automatic checkpoints

Every migration plan is reviewed and every template is security-scanned before deploy — but only a real stack conflict ever stops the run for a human decision.

AUTOMATIC

Plan approval

The migration plan and resource mapping table are logged for review once cfn-lint is fully clean; approval is automatic.

AUTOMATIC

Guardrail scan

checkov plus custom checks run next. Every finding is logged regardless of severity, and the run always continues.

HUMAN DECISION

Stack conflict

The only interactive prompt — fires only when the target stack already exists. Choose delete-and-recreate or cancel.

Once the stack gate clears, deployment is fully automatic — no confirmation prompt and no manual parameter entry. Parameter values resolve from files, environment variables, or the source Key Vault in a clear priority order.

Security & Guardrails

Scanning for risks and protecting secrets

Guardrail security scan

  • checkov — ~1000 built-in CloudFormation policy checks (encryption, public access, logging).
  • Hardcoded secrets — flags literal secret values outside NoEcho parameters.
  • Over-permissive IAM — flags wildcard Action / Resource / Principal.
  • Open network ingress — flags security groups open to 0.0.0.0/0 on sensitive ports.

Secrets handling

  • Secret values are wrapped so they print as *** in logs and state dumps.
  • A root logging filter redacts secrets before they reach any handler.
  • Plaintext never written to disk; real values are only revealed at the AWS API boundary.
  • No secrets passed via CLI flags — avoids shell history and process-list exposure.

Severity drives visibility, not blocking: every finding is logged to the run report and CLI, HIGH/CRITICAL ones are called out, and the run always auto-continues.

Knowledge Base & RAG

Grounded mappings, not guesswork

Each Azure resource type maps to a human-reviewed markdown document describing its AWS equivalent. The LLM retrieves the right docs before reasoning — so its plan is grounded in trusted guidance.

Mapping docs

Concept differences plus resource, parameter, and property mappings for each Azure → AWS pair.

Hybrid retrieval

Vector search (Chroma) fused with BM25 keyword scoring via reciprocal rank fusion for better recall.

Seed-and-grow

An unmapped resource type is logged and skipped automatically; the pipeline still migrates every resource it does understand.

Coverage grows by authoring a new mapping doc — no silent guessing, and no resource is ever migrated without a trusted, human-reviewed mapping behind it.

Evaluation & Calibration

Measuring quality and reliability

Benchmark harness

  • Curated reference examples with human-reviewed expectations.
  • Scores the LLM step: plan validity, parameter hygiene, resource-type accuracy, retrieval quality.
  • Also runs a trimmed pipeline (Agents 1–5) that never deploys — safe for CI-style checks.
  • Supports prompt-version comparison to tune the reasoning step.

Run-history calibration

  • Every real run appends its outcome to a history log.
  • Aggregate metrics: pass rate, human-intervention rate, deploy success rate.
  • Timing and Brier score track reliability over time.
  • A calibration report is regenerated after each run.

This two-layer approach separates prompt quality from operational reliability — important for a portfolio-grade capstone.
